# Index Key Value Collision (#371, #287) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Two values of one attribute written in one transaction are both stored, indexed and returned by every query path; file format moves to v8 with v7 auto-migration; v1–v6 are no longer readable.

**Architecture:** Append `value_bytes` + `asserted` to `EavtKey`/`AevtKey` and `asserted` to `AvetKey`/`VaetKey` (sort prefix unchanged). All key construction goes through per-key constructors. A v7 file is always sent down the existing index-rebuild path on open, which writes v8 B+trees and a v8 header. The query-time dedup key in `selective_fact_fetch` gains the encoded value. v1–v6 headers are rejected with a new `STG-028`.

**Tech Stack:** Rust (MSRV 1.89), postcard, cargo test / clippy / fmt, cargo bench (criterion).

**Spec:** `docs/superpowers/specs/2026-09-21-index-key-value-collision-design.md`

## Key finding from planning (read before Task 3/4)

On-disk B+trees are built from sorted `Vec`s (`build_sorted_index_entries` + `merge_sorted_vecs`), not `BTreeMap`s, so after a checkpoint **both** colliding entries are already on disk today. The value loss after checkpoint comes from the `selective_fact_fetch` dedup (Task 4); the EAVT/AEVT disagreement comes from `sort_unstable_by` putting the two equal-keyed entries in different orders, so "first seen" differs. The pending in-memory `BTreeMap`s (before checkpoint) lose a value through key overwrite (Task 3). Tests in each task target the state that task fixes.

fn three_paths(db: &Minigraf, ent: &str, attr: &str, marker: &str) -> [BTreeSet<String>; 3] {
    let eavt = rows(db.execute(&format!("(query [:find ?v :where [{ent} {attr} ?v]])")).unwrap())

        .unwrap(),
