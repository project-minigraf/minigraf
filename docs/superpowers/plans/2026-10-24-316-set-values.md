## Decisions not fixed by the spec

1. **Long-value reads become byte reads.** `DictReader::long_value` returns `String` and fails
   `STG-036` on non-UTF-8 bytes (`dict.rs:203`), and `find_long_value` compares candidates as strings
   (`dict.rs:219`). A set record is not UTF-8, so a string whose `hash64` collides with a set's would
   fail instead of missing. Add `DictReader::long_bytes(vref) -> Result<Vec<u8>>` (the cache keyed by
   `ValueRef` holds bytes), make `long_value` a UTF-8 view of it, and make the dedup lookup
   `find_long_bytes(&[u8])`, comparing bytes. `KeySource` gains `long_bytes` and `long_bytes_ref`;
   `long_value_ref(s)` becomes `long_bytes_ref(s.as_bytes())`.
2. **The `Encoder` stages long values as bytes.** `new_values: Vec<String>` / `new_long:
   HashMap<String, usize>` (`dict.rs:376-394`) become `Vec<LongValue>` keyed by bytes, where
   `LongValue { bytes, kind: Str | Set { prefix } }`, so `finish` builds `keys::long_str` or
   `keys::long_set` from the returned ref. One dedup table serves both kinds (spec §4.2).
3. **A set's v8 element encoding needs ids first.** `Encoder::value` for `Value::Set` assigns each
   keyword and ref element's id with `self.iid` / `self.eid` (as the scalar arms do), builds each
   element's `KeyValue` (`Str` for every string, whatever its length), encodes and sorts them
   (`keys::set_elements(&[KeyValue]) -> Vec<u8>`), then inlines (`KeyValue::Set`) or stages a long
   value. `keys::set_bytes_bound(&ValueSet) -> usize` (spec §3, no ids) lives in `keys.rs` next to it,
   so the WAL check and the encoder share one definition.
4. **Committed sets are decoded at scan.** `Cell::of_key` stays infallible and has no DICT access, so
   the committed scan (`scan.rs:462`) calls a new `Cell::of_key_with(&kf.v, ctx.keys)` that is
   `of_key` for every other value and, for `Set`/`LongSet`, decodes elements through
   `KeySource::ident_of`/`uuid_of` (and `long_bytes`) into `Scalar::Set(Arc<ValueSet>)` (spec §8).
   `Cell::of_value` maps `Value::Set` straight to it.
5. **Golden corpus.** The spec's §12 asks for a golden-file entry with sets. The corpus is v7 files
   (`tests/golden/`, never regenerated), and v7 has no sets, so there is nothing to add. The
   reopen, checkpoint and WAL-replay tests of step 6 cover persistence instead.
6. **`Value` match sites outside the crate's API.** `Value` becomes `#[non_exhaustive]`, which only
   affects other crates. Inside the crate every exhaustive match gets a real `Set` arm, never `_`, so
   the compiler finds each one: `types.rs`, `aggregate.rs`, `functions.rs`, `executor.rs`, `repl.rs`,
   `engine/project.rs`, `engine/cell.rs`, `engine/scan.rs`, `engine/plan.rs`, `prepared.rs`,
   `parser.rs`, `matcher.rs`, `db.rs`, `browser/mod.rs`, `storage/{index,keys,dict,verify}.rs`.
   Examples and tests in this repo that match exhaustively also get an arm.

## PR 3 — `collect-set`

Codes: #306 holds `PRS-115`–`118` and #180 holds `QRY-014` (its branch, not yet on `v3`), so the
spec's `PRS-121` (no binding) is **`PRS-122`**, its `PRS-122` (bad operand) is **`PRS-123`** and its
`QRY-014` (set value collected) is **`QRY-015`**. Whichever of these PRs lands second rebases and
keeps its numbers; gaps are allowed (`PRS-114` is followed by `PRS-119` today).

**Deviation from the outline: `collect-set` is an `Expr`, not a `WhereClause`.** It is
`Expr::CollectSet { entity, attribute }`, which the parser builds only as the whole expression of a
binding clause `[(collect-set ?e :a) ?s]`. The spec (§7.1) asks that it be checked, ordered, rewritten
and stratified as an expression clause, which is what `WhereClause::Expr` already is everywhere:
`check_expr_safety` (`INT-018` for an unbound `?e`), `optimizer::plan` (placed once `?e` is bound,
`Binders::expression` for an already-bound `?s`), magic sets and stratification (no edge), prepared
slots (none). A new clause would repeat each of these. The engine plans it as its own operator.

### Step 17. Parser

- `types.rs`: `Expr::CollectSet { entity: String, attribute: String }`, documented as clause-level
  only. Each exhaustive `Expr` match gets a real arm: `parser.rs` `expr_vars` and
  `optimizer::expr_vars` (`[entity]`), `prepared.rs` `collect_slots_from_expr`/`substitute_expr`
  (nothing), `plan.rs` `expr_vars` (the entity's slot), `executor.rs` `eval_expr` (`Err(())`:

  the operand given, a `$slot` included); then the binding: none is `PRS-122`, others as today
  (`PRS-069`, `PRS-068`). `parse_expr` refuses `collect-set` at any arity with `PRS-067`, so a nested
  one (`(in? 1 (collect-set ?e :a))`) and a one-operand `[(collect-set ?e) ?s]` never become a UDF.

  `tests/grammar/valid/query_collect_set.edn`, `tests/grammar/invalid/syntax/collect_set_*.edn` (no

## PR 4 — docs site and bindings

**Deviation from spec §9.** The spec predates #181, so it says no binding takes bind values. Since #181
every binding takes prepared bind values, and the UniFFI and Node/C fact-log records carry typed values,
so a set needs an input form as well as the JSON array output. Decided with the maintainer 2026-10-25:

| Family | Typed form (in and out) | Host sugar for a bind value |
|---|---|---|
| UniFFI (template, python, java, android, swift) | `MiniGrafValue::Set { value: Vec<MiniGrafValue> }` | Python `set`/`frozenset`; Kotlin/Java `Set`; Swift `Set` |
| C, Node | `{ "type": "set", "value": [ ...elements ] }` | Node: a JS `Set` |
| `BrowserDb` (core `src/browser/binds.rs`) | `{ type: 'set', value: [ ...elements ] }` | a JS `Set` |

- An element is a plain value or a typed *value* form (`string` … `null`); `entity`, `txCount`,
  `timestamp`, `anyValidTime` and `set` as an element are rejected. A nested set reaches core as
  `ValueSet::new` → API-021 where the form can express it (UniFFI); C/Node/BrowserDb reject it while
  reading the form with the same API-021 code.
- Plain arrays/lists stay rejected as bind values: they are kept free for a possible later collection
  binding.
- `execute()` JSON keeps spec §9: a set is a JSON array of its elements in canonical (`Value`) order. No
  other value becomes an array, so a set stays recognisable; elements lose their type as keyword and ref
  already do.
- UniFFI 0.31.1 generates the recursive enum for Python, Kotlin and Swift (checked 2026-10-25 in a
  scratch crate: Python round-trips `SET([INT64, TEXT])`; Kotlin `data class Set(value: List<…>)`, Swift
  `case set(value: [MiniGrafValue])`). In Kotlin the nested `MiniGrafValue.Set` shadows
  `kotlin.collections.Set` inside the sealed class only; wrapper code names `kotlin.collections.Set`
  explicitly where both appear.
