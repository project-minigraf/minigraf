# Implementation plan: optional distinct query results (#493)

Status: approved by Claude on 2026-10-26 after two review rounds.

Spec: `docs/superpowers/specs/2026-10-26-493-distinct-design.md`.

1. Verify a clean baseline on `origin/v3` in an isolated worktree. Run all tests,
   lint builds and other heavy verification on the designated bench machine when
   it is reachable and idle; keep the laptop for edits and reviews. Transfer the
   exact worktree contents before each check. Remove task-created remote scratch
   files and build outputs when they will no longer be reused.
2. Add a public integration suite `tests/distinct_test.rs`. Start with default-bag,
   projected-distinct, and parser boundary/duplicate-option acceptance checks; run
   the suite on the bench machine and observe rejection of the unsupported
   `:distinct` keyword.
3. Add default-false `DatalogQuery::distinct` in both constructors; parse the bare
   flag, closing the previous section and rejecting duplicates with `INT-012`.
   Extend `tests/grammar/grammar.pest` with `kw_distinct`/`distinct_section`, add
   the verifier token and update its filler-count assertions. Regenerate
   `docs/GRAMMAR.md` with `UPDATE_GRAMMAR_DOC=1 cargo test --test grammar_doc`.
   Add valid, duplicate-option semantic, and trailing-value syntax corpus files;
   check `$d` and `1` are refused as flag arguments. Reuse existing error codes;
   widen the affected error descriptions.
4. Add a projected `Distinct` step after `plan.find` is assigned and before
   the sort/limit tail. Give `Distinct` a projection mode: `JoinKey::group` keys
   and canonical float/float-set output, while `or` keeps its original behavior.
   Update the operator's comments to include query projection.
   Check all struct literal construction sites and prepared query cloning. Run
   the initial tests green, plus the grammar verifier.
5. Add and run acceptance cases in small groups: tuple keys; integer/float/zero,
   keyword/ref, strings/long strings/sets/NaNs; duplicate rows crossing 1,024-row
   internal batches; execute and cursor including prepared paths; joins/rules/or;
   aggregate inputs and hidden `:with` groups; windows; ordered pagination; temporal
   filtering; write transactions; committed/pending and checkpoint/reopen. Verify
   every behavioral assertion without UUID/value debug messages. Use test-hooks
   for reorder independence and hashed/correlated subplans. Use prepared bind
   values or direct test-only facts for NaNs, and chunked write transactions for
   long values. Confirm canonical floats and sets are independent of plan order.
6. Test a file-backed distinct cursor under a bound where the same query without
   distinct succeeds: `QRY-012`, cursor cleanup, and a later small query succeeds.
   In `src/query/engine/tests.rs`, check a query without `or` has a `Distinct`
   counter with the expected input/output counts. Pagination counts distinct rows.
7. Synchronize the five repository docs and make a separate worktree/branch for
   minigraf-docs. Gate syntax since v3.0.0; state bag defaults and older aggregate
   workaround. Run the docs builder/link checks according to that repo's guidance.
8. Run `cargo fmt --check`, `cargo test --quiet`, `cargo test --quiet --features
   test-hooks`, `cargo clippy --all-features -- -D warnings` (the repo's lint job),
   the grammar verifier at its default bound, and `cargo build --release` plus
   the v3 binary-size gate of 1,259,520 bytes. Test sources follow the repository's
   lint policy; its global panic-prevention lints exclude tests/examples/benches.
   Derive accurate test counts from fresh output and update docs.
9. Ask Claude for a final read-only review of both repository diffs and verified
   results before raising PRs. Verify each finding; fix and rerun affected checks;
   request follow-up review for material changes. Run an explicit-model read-only
   Codex review if required by standing project preferences.
10. Commit and push the reviewed changes, open the core PR against `v3` and docs PR
    against docs `main`, cross-link them, and monitor CI to green, fixing relevant
    failures. Do not merge or close the issue before merge. Report PR links,
    validation and review outcomes; note that closing keywords only take effect
    on the default branch, so the issue needs closing after the v3 PR merges.
