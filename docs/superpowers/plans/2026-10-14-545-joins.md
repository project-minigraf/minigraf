## Today's join rules

`PatternMatcher::join_with_pattern` (`src/query/datalog/matcher.rs`) joins the rows so far
with the next pattern in `optimizer::plan` order, in one of two ways:

- **Hash path.** Taken when the pattern's entity, or else its value, is a variable the
  rows already bind (the join variable). The pattern is matched against every fact
  without the rows, and the matches are hashed on `normalize_join_value` of the join
  variable (a keyword becomes the ref of the entity it names, `edn_to_entity_id`). Other
  shared variables are compared after the same normalisation. A merged row keeps the
  row's value for every variable the row binds.
- **Nested-loop path.** Taken otherwise: no shared variable, or one in the attribute
  position only, and for pseudo-attribute patterns. Bound variables are substituted into
  the pattern as constants (`apply_binding_to_component`) and matched with the constant
  rules of `match_component`: a keyword constant matches the keyword or the ref of the
  entity it names, a UUID constant a ref or a keyword naming it, a float constant any
  float within `f64::EPSILON`. A substituted variable is not rebound, so the row's value
  is kept.

Both paths compare `norm(a) == norm(b)`, with `norm` the keyword-to-ref normalisation.
The nested-loop path never compares a bound float: a bound entity or value variable
always takes the hash path, and the attribute position holds keywords only. Two answers
still depend on the plan (which differs under the `wasm` feature, where patterns are not
reordered):

- **Floats.** `Value`'s `Hash` hashes `-0.0` and `0.0` differently although `==` holds
  for them, so a hash join on a float key never pairs them, while the same pair as a
  non-key shared variable (compared with `==`) does. Elsewhere bound floats are compared
  within `f64::EPSILON` only where a `not` / `not-join` body substitutes them as
  constants (`substitute_pattern`), which is #546's anti-join.
- **Keyword or ref.** A variable bound to a keyword by one pattern and to the ref of the
  same entity by another returns the kind of whichever pattern ran first. In the
  nested-loop path this happens through the attribute position: a variable bound to a
  ref matches the attribute whose keyword names that entity.

## Design decisions not fixed by the spec

Settled with the maintainer on 2026-10-14.

1. **Float joins use IEEE `==`** (§5.4). Two bound floats are join-equal when `==` holds:
   `0.0` equals `-0.0`, and NaN equals nothing, NaN included. A float *constant* in a
   pattern keeps the `f64::EPSILON` match (spec §5.4, unchanged). In the executor this
   is a fix to `Value`'s `Hash`, which breaks the `Hash`/`Eq` contract for `-0.0` today:
   it now hashes `-0.0` as `0.0`. That covers every hash-keyed comparison of values: the
   pattern hash join, and the `not`, `not-join` and `or` keys. The epsilon comparison
   of bound floats substituted into `not` / `not-join` bodies is #546's to settle with
   the same rule (comment on #546).
2. **Keyword or ref: the first pattern in `:where` text order** (§5.4). When a variable
   is bound by several patterns, its value comes from the first of them in the query
   text. An expression binding (`[(f …) ?v]`) still overwrites the variable where
   `optimizer::plan` places it, and later joins keep the expression's value. The rule
   applies to the top-level `:where` of a query (the plan loops of
   `execute_query_on_executor` and `execute_query_with_rules`). `or` branches, `not`
   bodies and rule bodies keep today's rule; #546 and #548 decide theirs when they move
   to the engine.
   Pseudo-attribute patterns never replace a value: they read metadata of an entity
   the query has bound, and bind their entity variable only when nothing has.
3. **`IndexNestedLoopJoin` probes the entity position only.** The join is an
   `IndexNestedLoopJoin` when the inner pattern's entity is a variable the outer rows
   bind: one EAVT range per outer row, committed and pending. Every other join, including
   a join on the value or attribute position and a join with no shared variable (a cross
   product), is a `HashJoin`. Deviation from spec §6.3, which probes any position an
   index covers. Two reasons: the pending store has EAVT and AEVT indexes but no AVET,
   so a value probe reads the attribute's whole pending range once per outer row (every
   fact of an in-memory database); and a ref probe into the value position must also
   find the keyword values that name the entity, which no index holds.
4. **Pseudo-attributes keep today's plan-dependent rule, and a follow-up issue tracks
   it.** `:db/valid-from`, `:db/valid-to`, `:db/tx-count` and `:db/tx-id` read the fact
   of the last real pattern, in `optimizer::plan` order, that matched the same entity
   (the matcher's hidden `__f*_<uuid>` keys, overwritten by each match). The engine
   reproduces that. `:db/valid-at` joins with every visible fact of the entity, one row
   per fact. The issue is filed with PR 3.
5. **Join keys** (§5.4). Two cells are join-equal when:
   - both are `Eid`, or both `Iid`: the same id;
   - one is `Iid(k)` and the other `Eid(e)`: `e` is the id of `edn_to_entity_id(k)`
     (`IdSpace::keyword_eid`, a DICT id or a provisional one, cached like other DICT
     lookups);
   - both are `Val`: the same scalar, floats by decision 1. Long strings are one form:
     `Scan` turns a pending string over 64 bytes into `Long(vref)` when the committed
     value pages hold it (`KeySource::long_value_ref`), so equal long strings are equal
     cells (the #544 plan, decision 2, left this to #545).
   The planner normalises a slot's `Iid` cells only where the two sides can hold
   different kinds: an entity position holds `Eid`, an attribute position `Iid`, a value
   position or an expression binding either.
6. **Which cell a join keeps** (decision 2). The planner records, for each slot, the
   `:where` index of the pattern that bound it (or "expression"). When a pattern earlier
   in the text joins on that slot, the output row takes the pattern's cell; otherwise
   the outer row's. Static per join, no per-row cost.
7. **`HashJoin` build side.** The side with the smaller estimate: `optimizer`'s
   `pattern_cost` for the inner pattern against the smallest `pattern_cost` of the outer
   patterns (`branch_cost`). Ties build on the inner pattern. A key cell that contains a
   NaN never matches, so such rows are dropped on both sides. Bytes held are counted
   with #549.
8. **Join order** stays `optimizer::plan`'s (selectivity order; source order under
   `wasm`, spec §6.3). With decisions 1 and 2 the answer no longer depends on it, except
   for pseudo-attributes (decision 4).
9. **`PreparedQuery` plans per execution**, as in #544 (decision 10 there). Planning is
   a walk over the clauses; caching the operator tree with bind values as parameters
   waits for a measurement that shows planning matters. Deviation from spec §6.3's last
   paragraph, recorded on the issue.

## Steps

### 1. Float joins in the executor (PR 1)
- `Value`'s `Hash`: `-0.0` hashes as `0.0` (decision 1).
- Unit test in `types.rs`: equal values hash equally, `-0.0` and `0.0` included.
- Integration tests (`tests/join_rules_test.rs`): a join on a float value pairs `0.0`
  with `-0.0`, as the join key and as a shared variable after an entity key; a float
  constant still matches within epsilon. (A NaN cannot be stored: the parser has no
  NaN literal.)
- Comment on #546: the substituted-float epsilon in `not` bodies.

### 2. Keyword or ref by `:where` order in the executor (PR 1)
- `PatternMatcher::match_with_hint_seeded` takes the set of variables the pattern
  rebinds (decision 2). The hash path inserts the pattern's value for them; the
  nested-loop path takes the fact's value at the variable's first position (entity,
  attribute, value).
- The two executor plan loops track, per variable, the `:where` index of its binding
  pattern (expressions mark it as fixed) and pass the set.
- Integration tests: `[?a :friend ?b] [?b :name "Bob"]` (keyword-valued `:friend`)
  returns the keyword whatever the plan, and the reversed text the ref; the same through
  the attribute position and with a rule call; an expression's value is kept by a later,
  text-earlier pattern. They also pass with `--features wasm` (no reordering).

### 3. PR 1 checks
- `CHANGELOG.md` (v3.0.0, Breaking changes): the two rules and the queries whose answers
  change.
- `cargo fmt`, clippy (native, `wasm`, `browser`/wasm32), `cargo test`,
  `cargo test --features test-oracle`.

### 4. Join keys (PR 2)
- `IdSpace::keyword_eid`; `Scan` canonicalises pending long strings (decision 5).
- `cell::join_eq` and a hashable `JoinKey` (decisions 1, 5).
- Unit tests: keyword vs ref of the same entity (DICT and provisional), long strings
  committed vs pending, floats.

### 5. `IndexNestedLoopJoin` (PR 2)
- `src/query/engine/join.rs`. `Scan` takes a seed row: its `Term::Eq` positions compare
  with the seed's cells by `join_eq` (a new `Term::Join(slot)`, keeping `Term::Eq` for a
  variable repeated inside one pattern, which compares exactly as `match_fact_against_pattern`
  does), its entity range is the probe, and it keeps or replaces each joined cell by
  decision 6. A provisional entity id has only pending facts.
- Per outer batch: probes in row order; an outer row with many matches resumes the inner
  scan across output batches. `close` closes the outer side and the current probe.
- Counters: outer rows in, inner keys and facts read, rows out.

### 6. `HashJoin` (PR 2)
- Builds on one side (decision 7), streams the other, emits rows in the streamed side's
  order. An empty key is a cross product.

### 7. Planner v2 (PR 2)
- Eligible: every clause is a pattern with a real attribute, an expression, or a
  pseudo-attribute pattern on the first pattern's entity (#544's shapes); `:find` plain
  variables; as #544 otherwise. Pseudo-attribute patterns anywhere else wait for PR 3.
- Clauses in `optimizer::plan` order; the first pattern is a `Scan`, each later pattern an
  `IndexNestedLoopJoin` or a `HashJoin` (decision 3), each expression a `Filter`/`Bind`.

### 8. Oracle tests (PR 2)
- `tests/engine_oracle_test.rs`: two- and three-pattern joins on entity, value and
  attribute positions; cross products; keyword vs ref in both text orders; floats
  `0.0`/`-0.0`/NaN; long strings committed vs pending; pending shadowing committed in
  the inner pattern; in-memory and file-backed, before and after a checkpoint and a
  reopen; `:as-of` and `:valid-at` on joins.
- `cargo test --features test-oracle` over the whole suite: most multi-pattern queries in
  the existing suites now run on the engine.

### 9. PR 2 checks

### 10. Pseudo-attributes across joins (PR 3)
- Each real pattern's scan fills metadata columns only when a pseudo-attribute pattern
  may read it. A pseudo-attribute pattern reads, per row, the metadata of the last real
  pattern before it in plan order whose entity cell is join-equal to its entity
  (decision 4).
- Eligible when its entity term is the entity term of a real pattern planned before it
  (the matcher's fast path then always applies), or when no real pattern is planned
  before it (it then matches every visible fact of the entity: a `Scan` of `[e _ _]`
  with the metadata column). Other shapes stay on the executor.
- `:db/valid-at`: a join with `[e _ _]` and a constant column (the query's valid time,
  `Null` under `:any-valid-time`).
