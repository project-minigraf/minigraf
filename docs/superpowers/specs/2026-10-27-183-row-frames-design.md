# #183 Bounded sliding row frames — design

Date: 2026-10-27. Target: v3.0.0 on `v3`, based on `origin/v3` after #182 and #765. The maintainer moved the release target from v3.next to v3.0.0 before merge. The design and code received Claude approval.

## Goal and philosophy

Add `:rows N preceding` to Datalog window aggregates without changing stored data or the default frame. This is an additive, in-process query feature for ordered temporal/event data. No new dependency, configuration, service, file-format change, or public API break. Keep the implementation shared by all query entry points and covered by correctness, memory-budget, and performance checks.

## Language and semantics

Example: `(sum ?amount :over (:partition-by ?account :order-by ?time :rows 2 preceding))`.

`N` is a literal, nonnegative EDN integer in `0..=i64::MAX`. `preceding` is the plain symbol after it. The existing lexer also splits adjacent `2preceding` into the integer and symbol, so the grammar corpus accepts that spelling. Exactly one `:rows` option is accepted per `:over` list. Option order follows the existing flexible `:over` parser; `:order-by` remains required. `N=0` means current row only; `N=2` means up to two earlier physical rows plus current row. At a partition start the frame truncates. At a partition boundary it resets. `N` greater than partition length includes the whole prefix. No following/current-row/range frame syntax in this issue.

The row order is the existing window total order: `:order-by` value and direction, then the values of all variables named by plain `:find` elements and window arguments/partition/order keys in `:find` order, then input position. `aggregate::named_vars` includes the argument and keys of *every* window in the `:find`. The existing `value_order` breaks numeric ties: integer 1 precedes float 1.0, -0.0 precedes 0.0, and distinct NaN bit patterns have a defined order; other value classes are also totally ordered. An `Equal` comparison of all named-variable keys therefore does not hide distinct typed/bitwise values used by a window. In a grouped query, the parser requires every window variable to be a plain grouping variable, and the engine does not add `:with` keys when a window is present. Thus two rows tied through every named-variable key have the same visible plain columns and same input to every window. Swapping such rows may change which physical row gets a position but cannot change the answer bag. Keep that plan-independence guarantee and test it with optimizer reordering enabled and disabled, including integer/float, signed-zero, and NaN cases. Query results retain bag multiplicity until an explicit `:distinct`.

Peers with the same order key are separate positions for an explicit `:rows` frame, so they can have different results. An absent `:rows` retains the current default: an unbounded preceding frame ending at the *last peer* of the current row; all peers share the aggregate result. The existing window functions are exactly `sum`, `count`, `min`, `max`, `avg`, `rank`, `row-number`, `lag`, `lead`, and registered aggregate UDFs. `rank`, `row-number`, `lag`, and `lead` retain their current behavior when no frame is specified and reject an explicit frame because it does not define their output. This also prevents silently ignored options. The five built-in aggregates and registered aggregate UDFs accept `:rows`; `count-distinct` and `sum-distinct` remain rejected with PRS-031. An unknown UDF name is rejected at execution with the existing QRY-011, including when a query was prepared first.

The frame includes nil and nonnumeric values as rows. Existing function-specific stepping remains unchanged: count skips nil and returns 0 when none remain; sum skips nonnumbers and returns integer 0 when none remain; avg skips nonnumbers and returns nil when none remain; min/max skip nil and return nil when none remain; UDFs receive each value including nil. Aggregation still precedes windows in grouped queries. `:distinct`, final ordering, offset/limit and cursors still operate after window values are computed over all eligible rows.

## AST and parser

Add `WindowFrame` (initially `RowsPreceding(u64)`) and `frame: Option<WindowFrame>` to `WindowSpec`. `None` is the existing default. The lexer parses integers as `i64`; only a nonnegative `EdnValue::Integer` converts to `u64` in the AST. Parse `:rows` as exactly `Integer(N)` followed by lowercase plain symbol `preceding`; reject negative, float, missing, wrong suffix (including `:preceding` and case variants), duplicate, logic-variable, or bind-slot input with a new registered PRS code for malformed frame syntax. `-0` is accepted as zero because the existing lexer produces `Integer(0)`; `+2`, `2N`, and `2M` split into multiple tokens and fail frame validation with `PRS-124`; integers beyond `i64::MAX` fail in the lexer with `INT-008`. None are newly supported. Reject explicit frames on rank/row-number/lag/lead with a separate registered PRS code. These two codes are allocated after checking the current error registry and open branches. Add them to `docs/ERROR_REFERENCE.md` and the parser-verifier grammar. Existing accepted syntax and its errors remain unchanged; `:rows` was previously an unknown `:over` option (PRS-039), so its new malformed/unsupported errors are intentional.

`WindowSpec`, `WindowFrame`, and `ErrorCode` are behind private crate modules and are not part of the exported Rust API. The new AST field needs updates to internal struct literals. `FindSpec::display_name` is a column label, not a round-trip representation or query cache key; existing window labels omit `:over` details, and results/cursors are positional. `PreparedQuery` stores the parsed query directly; `Cursor` owns an already opened query and snapshot, with no query fingerprint. There is no normalized-AST cache or persisted rule/query form. Check final `:order-by` matching between otherwise identical window expressions with different frames, since it uses `FindSpec` equality.

## Evaluation

Extend the shared `aggregate::windows` calculation used by the engine; no second implementation. Retain the existing partition sort and output-to-input-row mapping. After #765 merges, partitions are slices of one charged sorted row-index vector; evaluate each bounded frame within its slice so it resets at the partition boundary. An explicit frame at sorted position `p` covers positions `p.saturating_sub(N)..=p`, with safe conversion on 32-bit targets. Keep `None` on the current peer-group path and lag/lead on their row-offset path. Keep the #765 `WindowColumnMeter` accounting for every result value, including strings/sets.

For the five built-in aggregates, maintain a sliding state as rows enter and leave the frame, giving O(R) evaluation per partition after sorting. `count` uses a non-nil count. Current `Running::Sum`/`Avg` already use `Sum`: an `i128` integer total plus a fixed-limb exact finite-float sum, rounded once at output. Extend that representation with reversible counters for NaNs, infinities, float presence, and signed zero; removal must be bit-for-bit equivalent to replaying the frame in existing `Running` semantics, including mixed numeric types and overflow saturation only at output. `min`/`max` use monotonic deques of row indices under the existing total value order, skipping nil; the deque must return the same typed/bitwise value as `Running::Extreme` for mixed values and NaNs. Reserve at most `min(partition length, N+1)` indices and charge their actual capacity to the window memory meter. Do not replace exact sums with rounded subtraction.

Registered aggregate UDFs have no inverse or merge API, so replay the current frame with a fresh accumulator for each row: O(R * min(N+1, R)) steps. When N covers the whole partition prefix, use one running accumulator and emit each row's value in O(R), including for UDFs; `Udf::value(&self)` already finalizes without consuming the accumulator. A middle-sized UDF frame on a large partition can cause billions of callbacks; there is no separate CPU step budget or cancellation check in this window loop, and the query memory limit does not prevent that cost. Document this clearly in the Datalog reference. A fresh UDF accumulator may allocate arbitrary memory outside the engine meter, as it already can for a default window; retain only one at a time and document this existing limit. A built-in sum holds constant-sized exact state; a deque holds at most R indices, and result payloads retain their #765 charging. The benchmark harness uses existing Criterion dev-dependency, so no new dependency is needed. The plan's timing gate covers small, middle, and large N for built-ins; any change of algorithm after a failed gate requires a spec revision and renewed review.
